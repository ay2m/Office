# المساهمة في «المكتب»

هذا الدليل خاصّ بـ**هذا المستودع** — `ay2m/Office`، مستودع الوثائق الداخلية.
(لمستودعات التطبيق أدلّة مساهمة خاصّة بها؛ وخطوات الإعداد وأوامر `npm run check:*` الخاصّة
بتطبيق الويب **لا** تنطبق هنا.)

**ابدأ من [`CLAUDE.md`](../CLAUDE.md) في الجذر** — فهو المرجع الموثوق لبنية هذا المستودع
وأعرافه. وهذا الملف هو الرفيق التشغيلي المختصر له.

## كيف تبدو المساهمة هنا

لا توجد شيفرة تطبيق في هذا المستودع. والتغيير يكون في الغالب أحد هذه الأشكال:

- **صياغة وثيقة أو تحريرها** — سياسة، أو مسودّة عقد، أو دليل عمل، أو مواصفة، أو دليل تشغيل (`.md`).
- **تحديث مُخرَج نهائي** — ملف `.docx` / `.xlsx` / `.pptx` يُنتَج خارج المستودع ويُودَع بوصفه ملفًا
  ثنائيًا.
- **إعادة التنظيم** — إعادة تسمية الملفات أو نقلها أو إعادة فهرستها (حدِّث
  [`_INDEX.md`](../_INDEX.md)، وإن تأثّرت النسخة العربية فحدِّث `ar/` في التغيير نفسه).

## الأعراف التي يقوم عليها هذا المستودع

- **غير مرتبطة بالهيئة العامة للطيران المدني.** فلاي قاكا منصّة تعليمية مستقلّة. لا تُوحِ مطلقًا
  بصفة رسمية للهيئة العامة للطيران المدني في أي وثيقة، ولا تختلق مرجعًا تنظيميًا أبدًا — بل أحِل إلى
  المصدر الرسمي للهيئة أو سمِّه.
- **البيانات الوصفية (front-matter) على كل ملف `.md`.** يحمل كل ملف محتوى بصيغة Markdown كتلة
  YAML القياسية (`title / section / doc_type / status / owner / last_updated / lang`). أما
  الملفات تحت أي مجلد `templates/` فتكتفي بمفتاح `title`. وملف `README.md` في الجذر مُعفى من فحص
  البيانات الوصفية وحده.
- **أعِد توليد ملف PDF مع كل تعديل على `.md`.** لكل ملف `.md` نسخة PDF جاهزة للطباعة تحت `_print/`.
  أعِد توليدها قبل الإيداع:
  ```bash
  cd tools/print
  npm ci            # مرة واحدة، أو بعد تغيير في الاعتماديات
  npm run build     # تزايدي — تُعاد معالجة الوثائق المتغيّرة فقط
  ```
  أودِع ملف PDF المُعاد توليده وملف `tools/print/.buildcache.json` المحدَّث **مع** تغيير `.md`
  نفسه. أما صفحات HTML فتُعالَج على حدة عبر `node build-html.mjs`.
- **الانضباط ثنائي اللغة.** ينبغي أن تحصل وثائق المحتوى الجديدة أو المتغيّرة جوهريًا في النهاية على
  نظير تحت `ar/` بالمسار نفسه، مُترجَم وفق [`ar/_GLOSSARY.md`](../ar/_GLOSSARY.md). ولا يفرض نظام
  التكامل المستمر تطابق الإنجليزية/العربية فرضًا صارمًا، لكن لا تدع النسخة العربية تنحرف بصمت.
- **المحتوى الحسّاس.** الوثائق القانونية والمالية والمتعلّقة بالموارد البشرية والمستثمرين هنا مادة
  تشغيلية حقيقية. اقتبس أو أعِد الصياغة بالحد الأدنى اللازم في رسائل الإيداع، وأوصاف طلبات السحب،
  والأدوات الخارجية.
- **التسمية.** أسماء الملفات بالأحرف اللاتينية الصغيرة بنمط kebab-case، بما في ذلك تحت `ar/`.
  والتواريخ في أسماء الملفات بصيغة `YYYY-MM-DD`. راجع اصطلاح التسمية في
  `06-operations-it/repo-health-report-2026-06-16.md` §6.

## قبل فتح طلب سحب (PR)

البوّابة السابقة لطلب السحب في هذا المستودع هي فاحص الوثائق — وهو نفسه ما يشغّله نظام التكامل
المستمر (`.github/workflows/docs-check.yml`):

```bash
cd tools/print
node check.mjs    # البيانات الوصفية + تغطية Markdown↔PDF + قِدَم الملفات + تغطية HTML↔PDF
```

ويُنهي بحالة غير صفرية عند أي مخالفة. ولا يحتاج الفحص نفسه إلى متصفّح.

## طلبات السحب (Pull requests)

- أبقِ التغييرات مركّزة؛ واشرح ماذا تغيّر ولماذا.
- يجب أن تكون جميع فحوص نظام التكامل المستمر خضراء.
- بمساهمتك، فإنك توافق على ترخيص مساهماتك بموجب
  [رخصة Apache الإصدار 2.0](LICENSE). أما **المحتوى** التنظيمي المقتبس في أي موضع فمملوك للهيئة
  العامة للطيران المدني وغير مشمول بتلك الرخصة.

من اللازم، أو وثيقة ما كان ينبغي إيداعها — **لا** تفتح مشكلة عامة. راسل القائم على الصيانة عبر
